# Technical presentations

Build the presentation around the audience's question and a clear central line: what they should understand, believe, or do by the end, and why the evidence supports it. Adapt the narrative, style, and deliverables to the assignment; do not impose a fixed slide count, sequence, or visual template.

## Brief and narrative

Before planning a new presentation, follow [questions.md](questions.md). Use [narrative review](references/brief-and-narrative.md) for practical tests.

Draft the narrative before layout: each slide's title, purpose, evidence or example, main message, transition, and estimated time. Choose the amount and form of text for the idea. Test the title sequence, logic, evidence, transitions, audience comprehension, and timing; revise gaps rather than adding filler. Make a separate script if requested or appropriate to the workflow, covering what is shown, the message, speech, actions, transitions and sources. Honor requested notes and formats.

## Visuals and evidence

Use accurate, readable figures that answer a specific question. Prefer editable native diagrams and tables when editability matters, and compute scientific plots from actual data or models. Internet images can be used when they add value: check the original source, attribution and reuse terms appropriate to the intended distribution, record source and any modifications, and preserve required attribution. Never present illustrative or generated images as evidence. For figures made with code or image generation, use [visual review](references/visual-review.md); inspect symmetry, arrows, positions, empty space, labels and final-size readability, and check their meaning against the intended model.

## Build and verify

Use the presentation authoring tools available in the target environment and follow any existing project instructions. Use the bundled [house toolkit](references/house-toolkit.md) as the default authoring and checking workflow for technical decks. Adapt its content, layouts and shared style to the audience, subject, language and assignment; do not copy its example narrative. Follow an explicit user requirement or existing project instruction when it conflicts with the kit, and do not overwrite an existing project's shared tools. If a required capability is unavailable in the kit, supplement it with suitable tools and explain the limitation.

Run relevant automated checks, inspect every rendered slide and script page, and test the requested presentation player where available. Review narrative and figures independently of machine checks: a passing checker cannot establish scientific accuracy, legibility in the room, or playback. Report actual results and any unavailable checks or limitations, and do not call unexecuted examples results.
